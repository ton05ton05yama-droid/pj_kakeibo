## 1. 用語（画面の言葉 ↔ 内部の概念）

画面に出す言葉の全体は仕様書 §1.1。ここではお金の計算に関わるものだけを、定義つきで並べる。

| 画面の言葉 | 内部名 | 定義 |
|---|---|---|
| 記録 | `expense` | 家計の支出1件。手入力の記録と、毎月の支払いから作られた行の2種類がある |
| 払った人 | `paid_by` | まさと・りさこ・共用のどれか。**共用は `paid_by = null`** |
| 共用 | `joint` | ふたりの共用口座・共用カード。人と同じ列に並ぶ「3人目の払い手」として扱う |
| （出さない） | `accounting_month` 帰属月 | その記録をどの月の精算に入れるか。手入力は日付の月（JST）。毎月の支払いの行は作った対象の月で、来月に回すと1か月進む |
| （◯月分） | `period_month` 対象月 | 毎月の支払いの行が「何月分」として作られたか。**来月に回しても変わらない**（§5.3）。手入力の記録には無い |
| 手取り | `net_income` | その月の各人の手取り。月ごとに保存する |
| 出す割合 | `contribution_rate` | 各人の割合（%）。人の設定に1つ持ち、出す額を決めたときにその月の値としても保存する（**本人だけ**が変えられる。2026-09-23。仕様書 §2.2・§12.1 Q26） |
| 出す額 | `contribution` | その月に各人が共用へ出すと決めた額。`floor(手取り × 割合 ÷ 100)`（割合は % の整数） |
| 給料の入り先 | `salary_to_joint` | その人の給料がどちらの口座に入るか（`false` ＝ 自分の口座 ／ `true` ＝ 共用口座）。人の設定に1つ持ち、出す額を決めたときにその月の値としても保存する（**決め直したときは、そのときの人の設定を取り込んで保存し直す**。ここだけ割合と違う。仕様書 §12.1 Q27・§11 #50。**本人だけ**が変えられる。仕様書 §2.2・§12.1 Q26） |
| 共用に入った給料 | `joint_salary` | その月、その人の給料のうち共用口座に入った分として精算額から引く額 ＝ 給料の入り先が共用なら `min(手取り, 出す額)`、そうでなければ 0（出す額を超えた分は共用に残す。§3.2） |
| 給料の残り | `salary_remainder`（＝ `salary_in` − `salary_applied`） | 共用に入った給料のうち、出す額を超えて**共用に残る**分 ＝ 給料の入り先が共用なら `手取り − 共用に入った給料`、そうでなければ 0。画面では S-20 の共用の行の下の注記「うち 給料の残り ◯円」（2人分の合計）だけに出る |
| もう払った分 | `advance`（立替） | その月、その人が自分のお金で家計の支出を払った合計 |
| （「共用で払ったもの」） | `joint_paid` 共用払い | その月、共用で払った記録の合計 |
| ふたりの支出（の合計） | `expense_total` 支出合計 | その月の記録の合計 ＝ もう払った分の2人分 ＋ 共用払い |
| 動かす額 | `settlement` 精算額 | 出す額 − もう払った分 − 共用に入った給料。正なら **共用へ入れる**、負なら **共用から受け取る**、0 なら **動かすお金はありません** |
| 共用に ◯円 残ります ／ 共用の残高から ◯円 出ます | `joint_balance` 共用の月間収支 | （Σ出す額 − 支出合計）＋ Σ給料の残り（§4）。**画面の共用の行に出すのはこの値**。給料が共用に入る人がいない月は Σ給料の残り ＝ 0 で、今までどおり Σ出す額 − 支出合計 |
| （出さない） | `joint_net` 共用の過不足（出す額ベース） | Σ出す額 − 支出合計。V4 の左辺で、`joint_balance` ＝ `joint_net` ＋ `salary_remainder`（§4） |
| 金額待ち | `amount is null` | 毎月の支払いの行のうち、その月の金額がまだ無いもの（ひな形の種類 `amount_kind = variable` もこの語で呼ぶ） |
| 来月に回す | `defer` | 金額待ちの行の帰属月を翌月にする |
| 今月はなし | `skip` | 毎月の支払いの行を、消さずに「その月は無い」状態にする |
| この金額で精算 | `confirm` | 月を精算中にして金額をロックする |
| 入れた ／ 受け取った | `transfer_check` | 動かす額のやりとりが済んだことのチェック |
| 精算をやり直す | `reopen` | 精算中・精算済みの月を、月が終わっていなければ進行中、終わっていれば締め待ちに戻す（§2.2） |
| 済んだ分 | `transferred` | やり直す前に付いていたチェックの額の合計（符号つき。§7） |
| あと ◯円 | `remaining` | やり直した後に、まだ動かす必要がある額 ＝ 動かす額 − 済んだ分 |

画面で使わない言葉（拠出・立替・精算額・差額・赤字・黒字など）は仕様書 §1.2。コードとDBでは内部名を使ってよい。

## 2. 月の状態機械

### 2.1 4つの状態

| 状態 | 内部 | 期間 | 持ち方 |
|---|---|---|---|
| 進行中 | `open` | その月の1日〜末日（JST）で、まだ［この金額で精算］を押していないあいだ | **保存しない**。今日の日付から決まる |
| 締め待ち | `closing` | 翌月1日 0:00（JST）〜［この金額で精算］まで。やり直した後もここ。**「月が終わったのに、まだ精算していない」という意味**で、赤い点・お知らせ行の条件1に使う（仕様書 §3.2） | **保存しない**（やり直した後だけ `month_settlements.status = 'reopened'` の行が残る） |
| 精算中 | `confirmed` | ［この金額で精算］〜チェックがそろうまで | `month_settlements.status = 'confirmed'` |
| 精算済み | `settled` | 動かすお金がある人すべてにチェックが付いた後 | `month_settlements.status = 'settled'` |

- 進行中と締め待ちは日付だけで決まるので、cron も「月が変わった」ことを書き込む処理も要らない（仕様書 §4.0.2、platform.md §1.4）。
- **精算を始められる時期の縛りは無い**（2026-09-23 の決定。仕様書 §12.1 Q2）。`open`（月の途中）からでも［この金額で精算］を押せる。画面では S-20 `estimate` の文字ボタン［この月を精算する］で `prep` ／ `ready` にしてから押すが、**それは画面の状態だけで DB には持たない**（本書が扱うのは月の状態 4つだけ）。
- 判定は DB 側の関数で行い、2台で同じ結果にする（`private.month_status()`。`docs/04_data_model.md` §5）。「今日」は DB のサーバー時刻を JST にしたもので、端末の時計は使わない（本書の決め。§10 C10）。
- 月の範囲は、家計を作った月（`households.start_month`）から今月まで。

```
進行中 open ──────────────────────┐ この金額で精算（月の途中でも押せる。画面では
  │ 翌月1日 0:00（JST）            │   S-20 estimate の［この月を精算する］→ prep / ready のあと）
  ▼                                │
締め待ち closing ◀─────────────┐  │ 精算をやり直す（精算中・精算済みのどちらからも。
  │ この金額で精算               │  │   チェックは「済んだ分」として残る。戻り先は
  ▼                              │  │   月が終わっていなければ open、終わっていれば closing）
精算中 confirmed ◀───────────────┼──┘
  │ ▲                            │
  │ │ チェックを外す              │
  ▼ │                            │
精算済み settled ────────────────┘
  （動かすお金がある人すべてにチェック → 自動で精算済み。2人とも 0円なら、この金額で精算と同時に精算済み）
```

### 2.2 移り変わりの条件

| 移り変わり | きっかけ | 条件 | 保存すること |
|---|---|---|---|
| `open` → `closing` | 翌月1日 0:00（JST） | なし（日付だけ） | なし |
| `open` ／ `closing` → `confirmed` | だれかが［この金額で精算］ | (1) 2人とも、その月の出す額が決まっている<br>(2) その月の金額待ちが 0件<br>(3) 前の月が `confirmed` か `settled`（家計を作った月は前の月を問わない）<br>(4) 押した人が見ていた数字と、いまの数字が同じ（本書の決め。§8・§10 C3） | 各人の 出す額・もう払った分・動かす額・済んだ分、月の 支出合計・共用払い・出す額の合計・共用の過不足、押した人・時刻 |
| `confirmed` → `settled` | 最後のチェックが付いた（自動） | 動かす額（やり直し後は「あと」の額）が 0 でない人すべてにチェック | 時刻（「精算済み 10/2」） |
| `open` ／ `closing` → `settled` | ［この金額で精算］ | 上の (1)〜(4) に加えて、2人とも動かす額（やり直した後は残り）が 0 | 確定と同じ ＋ 時刻 |
| `settled` → `confirmed` | チェックを外した（元に戻すを含む） | — | 時刻を消す |
| `confirmed` / `settled` → `open` ／ `closing` | だれかが［精算をやり直す］ | なし。**戻り先は日付で決まる**（月が終わっていなければ `open`、終わっていれば `closing`） | 押した人・時刻・どの状態から戻したか。チェックは消さない |

- 足りない条件のまま押したときの1行（「先に8月を精算してください」など）は仕様書 §1.4。条件 (1)(2) が欠けている月は、そもそも S-20 が `undecided`・`prep` になり［この金額で精算］を出さない。
- 押せるのは2人とも（仕様書 §2.2、§12.1 Q6。**2026-09-23 に確定**: 2人の承認にはしない）。片方が押せば進み、押した人と時刻を残す。
- 前の月が締め待ちのまま次の月は精算中にできない（仕様書 §6.4、§12.2 Q22）。チェックが残っている（前の月が精算中の）ままなら、次の月を精算中にしてよい。**月の途中でも精算できるようにした（§12.1 Q2）後も、この順番のきまりは変えない**（条件 (3)）。前の月が進行中ということは起きない（月は古い順に並ぶ）。

### 2.3 ロック（精算中・精算済みの月でできないこと）

ロックの時点は［この金額で精算］（振込の前。仕様書 §12.1 Q1。**2026-09-23 に確定**: 精算完了ではない）。精算中・精算済みの月では、次のことをだれもできない。

- その月の記録を足す・直す・消す（日付を変えてその月に入れる・その月から出すことも含む）
- その月の毎月の支払いの行を直す・今月はなしにする・来月に回す、ほかの月からその月へ回す
- その月の出す額を決める・変える
- その月の毎月の支払いの行を新しく作る（`ensure_month` はロック中の月を飛ばす）

ロックしていても、ひな形（毎月の支払い）・出す割合・呼び名は変えられる。作ってある行と決めた出す額は変わらない（仕様書 §2.2）。

**月の途中で精算した月も同じようにロックされる**（2026-09-23。仕様書 §12.1 Q2）。その月の残りの日の支出を足す・直すには［精算をやり直す］が要る（やり直すと、月が終わっていないので `open`〈進行中〉に戻る）。`ensure_month` はロック中の月を飛ばすので、月の途中で精算したあとは、その月のひな形の行も作られない。

### 2.4 S-20 の状態との対応

S-20 の状態キー（仕様書 §4 S-20「状態の決め方」）は、月の状態と次の4つの数から上から順に決まる。判定は DB の関数 1か所（`private.s20_state()`）で行う。

| 順 | 状態キー | 条件 |
|---|---|---|
| 1 | `settled` | 月が精算済み |
| 2 | `transfer` | 月が精算中 |
| 3 | `empty` | その月に出す額を決めた人が0人で、前の月にも0人 |
| 4 | `undecided` | その月に出す額を決めた人が2人未満 |
| 5 | `estimate` | 月が進行中で、画面が精算のモードでなく（［この月を精算する］を押していない）、その月にチェックの記録も無い |
| 6 | `prep` | 精算に進む月※ で、その月の金額待ちが1件以上 |
| 7 | `redo` | 精算に進む月※ で、その月にチェックの記録（済んだ分）がある（済んだ分の合計が 0 でも。仕様書 S-20） |
| 8 | `ready` | 精算に進む月※ で、上のどれでもない |

※ **精算に進む月** ＝ 締め待ちの月、または**月の途中で［この月を精算する］を押した月**（そのあとやり直してチェックの記録が残っている月を含む）。

- 5〜8 は、月の状態（`open` ／ `closing`）とチェックの記録の数に加えて、**画面が精算のモードかどうか**（`p_settle_mode`）で決まる。このモードは**端末の中だけの値で DB に保存しない**（仕様書 §12.1 Q2・§11 #45）ので、`private.s20_state()` には引数として渡す（`docs/04_data_model.md` §5）。渡さなければ今までどおり `estimate` になる。

### 2.5 元に戻す（6秒）

仕様書 §3.7 のとおり、どの移り変わりも6秒のあいだはトーストの「元に戻す」で前の状態に戻る。6秒を過ぎたら、精算は［精算をやり直す］、チェックはもう一度押して外す。

| 操作 | 元に戻すと | 戻せないとき（本書の決め。§10 C11） |
|---|---|---|
| 出す額を決める | 決める前に戻す（新しく作った行は消し、上書きした行は手取り・**給料の入り先**・決めた人・時刻を前の値に戻す。割合はもともと動かないので戻さない。前の値はサーバーが控えたもので、端末からは受け取らない。`docs/04_data_model.md` §8.3） | 月が精算中・精算済み、そのあと決め直された、または決めたのが自分でない |
| この金額で精算 | 月が終わっていなければ進行中、終わっていれば締め待ちに戻る（§2.2）。保存した値は捨て、確定の回数（`round`）も戻す | その回にもうチェックが付いている |
| 入れた ／ 受け取った | チェックを外す。精算済みになっていたら精算中に戻る | — |
| （自動の）精算済み | 最後に付いたチェックを外して精算中に戻る | — |
| 精算をやり直す | やり直す前の状態（精算中か精算済み）に戻る | やり直した後に数字が変わった（記録・出す額が直された） |
| 毎月の支払いを足した | ひな形と今月分の行を消す | 作った人でない・作ってから1分を過ぎた・行が直された（本書の決め。§10 C13） |

## 3. 計算式

### 3.1 対象にする記録

月 m の計算に入れるのは、次のすべてを満たす記録。

- 帰属月が m（`accounting_month = m`）
- 金額が入っている（`amount is not null`。金額待ちは入れない）
- 今月はなしでない（`skipped = false`）
- DB に届いている（端末に保留した「未送信」は、送れるまで入れない。仕様書 §3.6）

### 3.2 式

```
立替_i      ＝ Σ amount（paid_by = i の記録）             … 画面では「もう払った分」
共用払い    ＝ Σ amount（paid_by = null の記録）
支出合計    ＝ 立替_まさと ＋ 立替_りさこ ＋ 共用払い
出す額_i    ＝ floor(手取り_i × 割合_i ÷ 100)              … 割合は % の整数（§6）
共用に入った給料_i ＝ 給料の入り先が共用なら min(手取り_i, 出す額_i)、そうでなければ 0
精算額_i    ＝ 出す額_i − 立替_i − 共用に入った給料_i        … 画面では「動かす額」
給料の残り_i ＝ 給料の入り先が共用なら 手取り_i − 共用に入った給料_i、そうでなければ 0
共用の月間収支（joint_balance） ＝ Σ手取り(給料が共用に入る人) ＋ Σ(正の精算額) − 共用払い − Σ|負の精算額|
                              ＝ （Σ出す額 − 支出合計）＋ Σ給料の残り   … V11（§3.3）
共用の過不足（joint_net） ＝ Σ出す額 − 支出合計                          … V4（§3.3）
済んだ分_i  ＝ Σ そのカードに付いていたチェックの額（入れた ＋、受け取った −）
残り_i      ＝ 精算額_i − 済んだ分_i                       … 画面では「あと ◯円」
```

- 向き: `精算額_i > 0` → 「共用へ入れる」、`< 0` → 「共用から受け取る」、`= 0` → 「動かすお金はありません」（チェック不要・最初から済み）。やり直した後は `残り_i` で同じように決める。
- 金額は画面ではいつも正の数で出し、向きは矢印と動詞で表す（仕様書 §6.1）。DB と計算の中では符号つきで持つ。
- 出す額は、その月に決めたときの手取り・割合・**給料の入り先**・出す額を保存して使う。あとで割合や給料の入り先を変えても、**決め直さないかぎり**決めた月の出す額と精算額は変わらない。決め直した（S-21 でもう一度［決める］を押した）ときも、**割合はその月に保存した値**を使う（仕様書 S-21。給料の入り先だけは違う。次の行）。人の設定の**割合**が使われるのは、その月にまだ出す額を決めていない人の行を新しく作るときだけ。
- **給料の入り先だけは、決め直すとその人のいまの設定を取り込む**（2026-09-23。仕様書 §12.1 Q27・§11 #50）。割合は「これからこうする」という取り決めなので決めた月の値を動かさないが、給料の入り先は「その月の給料が実際にどこへ入ったか」という**事実**なので、S-33 で直してからその月を決め直せば合わせられる。新しく作る行はどちらも人の設定から取る（今までどおり）。精算中・精算済みの月は決め直せない（§2.2 のロック）ので、取り込みも起きない。元に戻す（`undo_decide_contributions`）では、前の給料の入り先にも戻る（`docs/04_data_model.md` §8.3）。
- **給料の入り先が共用のとき**（2026-09-23。仕様書 §12.1 Q25）: 手取りのうち**出す額まで**が共用に入っているものとして精算額から引く。**出す額を超えた分は共用に残す**（毎月まるごと返さない。仕様書 §11 #47）。**共用に入る額は手取り全額**で、「いくら入るか」を別に入れる欄は作らない（仕様書 §11 #49）。
  - 割合は 0〜100 の整数なので `出す額_i ≦ 手取り_i` がいつも成り立ち、`min` は実際には `出す額_i` を返す（`min` は守り。§9.7 のエッジケース）。だから**給料が共用に入る人の精算額は `−立替_i`** になり、画面では「もう払った分をそのまま共用から受け取る」形になる（立替が 0 なら「動かすお金はありません」）。
  - 手取りが未入力の月（出す額を決めていない月）は、共用に入った給料も給料の残りも 0（S-20 は `undecided`）。
  - 向きと動詞は今までどおり結果の符号で決める。**カードに「給料」の字は出さない**（仕様書 §6.1 の13）。
- 精算中・精算済みの月の表示は、［この金額で精算］の時点に保存した値から出す（仕様書 §6.2）。保存するのは、各人の **出す額・立替・精算額**（共用に入った給料を引いたあとの額）と、**支出合計・共用払い・`joint_net`**。**`共用に入った給料` と `給料の残り` は保存しない**（ロックされた `month_contributions` の 手取り・給料の入り先・出す額から `min(手取り, 出す額)` で出す。`docs/04_data_model.md` §2.7）。ロック中は記録が変わらないので、その月の記録から計算し直しても同じ値になる（あとで S-33 で給料の入り先を変えても、精算中・精算済みの月は動かない）。

### 3.3 いつも成り立つこと（検算）

仕様書 §9.6 の V1〜V11 をモックの検算パネルが毎回確かめる。実装でもテストに入れる。

- V1 支出合計 ＝ 立替_まさと ＋ 立替_りさこ ＋ 共用払い
- V4 `joint_net` ＝ Σ出す額 − 支出合計 ＝ Σ精算額 ＋ Σ共用に入った給料 − 共用払い（式の変形なので、ずれたらどこかの合計の取り方がまちがっている。給料が共用に入る人がいない月は Σ共用に入った給料 ＝ 0 で今までの2項の式と同じ）
- V5 **共用に入った給料がすべて 0 の月で** 2人とも精算額 < 0 なら、共用の過不足（`joint_net`）< 0（2人とも受け取る月は、必ず共用の残高から出る月）。反例: 2人とも共用に入る月は 精算額 −37,510・−22,070 でも `joint_net` ＝ 1,870・`joint_balance` ＝ 313,870 で正（仕様書 §6.3 ケースN のエッジケース。文言は仕様書 §9.6 が正本）
- V6 残り ＝ 精算額 − 済んだ分
- V7 金額待ち・今月はなし・未送信は合計に入れない
- V11 Σ手取り(給料が共用に入る人) ＋ Σ(正の精算額) − 共用払い − Σ|負の精算額| ＝ （Σ出す額 − 支出合計）＋ Σ給料の残り（通帳の動きと、式で出した過不足が一致する。給料が共用に入る人がいない月は Σ給料の残り ＝ 0 で V4 と同じ式になる。数値は §9.7）

## 4. 共用の過不足

- 画面（S-20 の共用の行）に出すのは **`共用の月間収支`（`joint_balance`）＝ `joint_net` ＋ `salary_remainder` ＝ （Σ出す額 − 支出合計）＋ Σ給料の残り**。その月、共用口座に「入ってくるはずの額」と「出ていく額（その月の支出すべて）」の差。給料が共用に入る人がいない月は `salary_remainder` ＝ 0 で `joint_balance` ＝ `joint_net` ＝ `Σ出す額 − 支出合計` になり、**今までの月の表示は1円も変わらない**。
- `joint_net`（出す額ベースの過不足）は意味を変えずに残す（検算 V4 の左辺。§3.3）。精算の表に保存するのも今までどおり `joint_net` で、`joint_balance` は `joint_net` ＋ `salary_remainder` で出す（`docs/04_data_model.md` §2.7）。
- **給料が共用に入る人がいる月**（2026-09-23。仕様書 §12.1 Q25）: 共用口座には、その人の**手取りが全額**入る。そのうち出す額のぶんは「出す額を払った」ことになり（精算額から引く）、超えた分（`給料の残り`）はそのまま共用に貯まる。だから通帳の動きは `Σ手取り(共用に入る人) ＋ Σ(正の精算額) − 共用払い − Σ|負の精算額|` で、これが上の式と一致する（検算 V11。§3.3・§9.7）。
- 画面（S-20 の共用の行）はこの値をそのまま「共用に ◯円 残ります」に出し、**給料が共用に入る人がいる月だけ**（**給料の残りが 0 の月は出さない**）、その下に注記「うち 給料の残り ◯円」を1行添える（内訳を示すだけで、行を2つに割らない。仕様書 S-20）。
- 正なら「共用に ◯円 残ります」、負なら「共用の残高から ◯円 出ます」、0 なら「共用の残高は変わりません」（仕様書 §1.1）。どれも警告の色にしない。
- **「出す額の合計が共用に入る」とは書かない。** 実際に共用口座へお金が動くのは「共用へ入れる」人の分（と、給料が共用に入る人の手取り）だけで、自分のお金で払った分（もう払った分）はすでに家計のために使われている。給料が共用に入る人がいない月に `Σ精算額 − 共用払い` と同じ値になるのはこのため。
- 共用口座の残高そのもの・何か月「出ます」が続いたかは扱わない（仕様書 §12.1 Q14）。
- 見込み（進行中の月）では「共用に ◯円 残る見込み」「共用の残高から ◯円 出る見込み」「共用の残高は変わらない見込み」とし、金額待ちを含まないことを添える（仕様書 §1.1、S-20 `estimate`）。

## 5. 毎月の支払いの行（金額待ち・来月に回す・今月はなし）

### 5.1 行の作り方

- ひな形1つにつき、**対象月（◯月分）ごとに1行**だけ作る。作るのは、その月の画面（支出・精算）かアプリを開いたとき（`ensure_month`）。2台が同時に開いても二重にならない（一意制約。`docs/04_data_model.md` §3）。
- 作る範囲は、ひな形を作った月から今月まで。ロック中の月・支払いをやめた月からは作らない。
- 行の日付はその月の1日。名前・カテゴリ・払う人・金額は、作った時点のひな形の値を写す。ひな形をあとで直しても、作った行は変わらない（仕様書 §6.5）。
- 毎月同じ → 金額入りで作る。金額待ち → 金額なし（`amount is null`）で作る。

### 5.2 行の状態と計算への入り方

| 行の状態 | 条件 | 計算に入るか | 精算の条件 |
|---|---|---|---|
| 金額あり | `amount` あり、`skipped = false` | 入る（払う人の「もう払った分」か共用払い） | — |
| 金額待ち | `amount is null`、`skipped = false` | 入らない。見込みには「金額待ち n件を含みません」 | **1件でも残っていたら精算中にできない**（`prep`。月の途中に精算するときも同じ） |
| 今月はなし | `skipped = true` | 入らない | 片付いたものとして扱う |
| 来月に回した | 帰属月が対象月より後 | 翌月の計算に入る | 元の月では片付いたものとして扱う |

### 5.3 来月に回す

- できるのは、**金額待ちの行**で、**翌月がロックされていない**ときだけ（仕様書 S-15）。2026-09-23 に「その行の帰属月が終わってから」の条件を外した（仕様書 §12.1 Q2）ので、**今月（進行中の月）の金額待ちでも回せる**。月の途中に精算するとき、請求が来ていない行をここで片付けられるようにするため。
- 帰属月を1か月進める。対象月（「（9月分）」の表示）と行の日付は変わらない。
  - 例: 電気代（8月分）は 9/1 に回され、日付 8/1・対象月 8月・帰属月 9月の行になった（s04）。9月の金額待ちに出て、9/10 にりさこが 9,840 を入れ、9月の共用払いに入った。
  - 元の月（8月）の支出には「電気代（8月分）　9月に回しました」を出す（金額は出さない。見せ方は仕様書 S-10）。これは「対象月 ＝ 8月、帰属月 ≠ 8月」の行として探す。
- 払う人が個人の行を回すと、その人の「もう払った分」も翌月に移る（金額が入るのは翌月なので、元の月の計算にはもともと入っていない）。
- 翌月でもまだ金額が分からなければ、もう一度回せる（翌々月がロックされていないときだけ。本書の決め。§10 C12）。
- 元に戻すと帰属月を1か月戻す。対象月より前には戻らない。

### 5.4 今月はなし

- 行を消さずに `skipped = true` にする（消すと `ensure_month` がまた作ってしまうため。仕様書 §6.5）。金額が入っている行にも、金額待ちの行にも使える。
- 計算には入らない。元に戻すと `skipped = false` に戻る。

### 5.5 だれが直せるか

毎月の支払いの行は2人とも直せる（金額・払った人・今月はなし・来月に回す）。カテゴリ・名前・日付は直せない（仕様書 §2.2）。金額を入れた人と時刻を残す（「金額: まさと 10/1」）。

## 6. 端数

- 端数が出るのは **出す額だけ**。`floor(手取り × 割合 ÷ 100)`、1円未満を切り捨てる（仕様書 §6.2・§6.3 ケースL、§12.2 Q20）。
- 割合は **% の整数（0〜100）** として持ち、`手取り × 割合 ÷ 100` を整数の割り算で計算する（どちらも 0 以上なので切り捨てと同じ）。浮動小数点を使わない。例: `283,457 × 40 ÷ 100 ＝ 11,338,280 ÷ 100 ＝ 113,382`（ケースL）。
  - 小数の割合（例 37.5%）は使わない（仕様書 §6.2）。S-33 の入力も整数（`inputmode="numeric"`、「0〜100で入れてください」）。
- それ以外（記録の金額・もう払った分・**共用に入った給料**・**給料の残り**・動かす額・共用の過不足）はすべて円の整数の足し算・引き算で、端数は出ない（`min(手取り, 出す額)` も整数どうしの比較で、丸めは起きない）。
- 記録の金額は 1〜9,999,999（テンキーは7桁まで。仕様書 S-12）。手取りは 0〜9,999,999（7桁まで。`net_income × 100` が 32bit 整数に収まる。0 も入れられ、手取りが無い月は 0 で出す額も 0。仕様書 S-21）。

## 7. やり直した後の差額

### 7.1 決まり

- ［精算をやり直す］で月は進行中か締め待ちに戻り（§2.2）、付いていたチェックは消さずに「済んだ分」として残る。
- 戻った月（進行中か締め待ち）のあいだは記録・出す額・毎月の支払いの行をふつうに直せる。S-20 は `redo` になり、カードには **残り（あと ◯円）と向きだけ** を出す（仕様書 §6.3 ケースI）。
  - `残り_i > 0` → 「[人] → [家] 共用へ入れる　あと ¥◯」
  - `残り_i < 0` → 「[家] → [人] 共用から受け取る　あと ¥◯」
  - `残り_i = 0` → 「済み（¥◯ 入れた）」
- **済んだ分との差の向きが逆なら、矢印と動詞も逆にする**（入れたのに受け取る側になった、など）。
- 共用の行は、やり直した後の全体の数字（Σ新しい出す額 − 新しい支出合計）で出す。済んだ分は関係しない。
- もう一度［この金額で精算］を押すと、そのときの済んだ分をカードごとに保存し、以後のチェックは **残りの額** に対して付ける。残りが 0 の人はチェック不要。残りが 0 でない人すべてにチェックが付けば精算済みになる（本書の決め。§10 C2。仕様書 S-20 `transfer` は、やり直したあとはカードに「あと ◯円」と向きを出し、数字の無い式を出さないことだけを書いている）。
- やり直しは何回でもできる。済んだ分は、それまでの全部の回のチェックの合計（符号つき）。

### 7.2 例

| # | 状況 | 済んだ分 | 新しい精算額 | 残り | 画面 |
|---|---|---:|---:|---:|---|
| I-1（見本データ 10/3） | 精算済みのあと、まさとが 9/28 のハンガー 3,300（自分のお金）を見つけた | まさと ＋82,490 | 120,000 − 40,810 ＝ 79,190 | 79,190 − 82,490 ＝ **−3,300** | 「[家] → [ま] 共用から受け取る　あと ¥3,300」 |
| 同上 | りさこは変わらない | りさこ ＋65,930 | 65,930 | 0 | 「済み（¥65,930 入れた）」 |
| I-2 | まさとの同じ記録（コンビニ 1,280）が二重に入っていて消した | ＋X | X ＋ 1,280 | **＋1,280** | 「[ま] → [家] 共用へ入れる　あと ¥1,280」 |
| I-3 | 2,000 入れたあと、正しい精算額が −1,000 だった | ＋2,000 | −1,000 | −1,000 − 2,000 ＝ **−3,000** | 「共用から受け取る　あと ¥3,000」 |

I-1 の共用: 208,000 − 209,430 ＝ −1,430 → 「共用の残高から 1,430円 出ます」。

## 8. 2台の同時操作

### 8.1 考え方

1. **判定と確定は DB の関数（RPC）で行う。** 画面が持っている数字を信じて書き込まない。2台で同じ関数を呼ぶので、同じ結果になる（仕様書 §6.2）。
2. **精算の操作は冪等にする。** ［この金額で精算］［入れた／受け取った］［精算をやり直す］は、何度押しても1回分と同じ結果になる。チェックは「付け外しを反転する」のではなく「付ける／外す」を指定して送る。
3. **月ごとに順番に並べる。** 確定とチェックは、その月の排他ロック（`pg_advisory_xact_lock`）を取ってから行う。記録・出す額の書き込みは同じ月の共有ロックを取ってからロック中かを確かめる。これで「確定と同時に記録が入り、確定した数字に入らないまま保存される」ことが起きない。
4. **リアルタイム同期は使わない。** 相手の操作は、アプリを開き直したとき・タブを選び直したとき・画面に戻ったときに取り直して反映する（仕様書 §6.3 ケースJ）。
5. **精算とロックの操作は端末に保留しない。** オフラインで押したら「オンラインで直せます」（仕様書 §3.6）。保留してよいのは記録の追加だけ。

### 8.2 操作ごとの扱い

| 同時に起きること | 結果 |
|---|---|
| 2人がほぼ同時に［この金額で精算］ | 先に届いた方で精算中になる。遅れた方は「もう精算中」が返り、画面に「9月はもう精算中です」と出して精算中の表示に更新する |
| 相手が記録を直した直後に［この金額で精算］ | 押した人が見ていた「あと ◯円」（カードの額）を一緒に送り、いまの数字と違えば確定せず、最新の数字を返す（本書の決め。このときの文言は仕様書に無い。§10 C3） |
| 精算中にする瞬間に、相手が記録を保存 | どちらかが先に通る。記録が後なら「9月は精算中です（直すには精算をやり直します）」。記録が先なら、その記録を含めて確定する |
| 2人が同じカードのチェックを押す | 「付ける」同士なら1つだけ付く。押した人・時刻は先に届いた方 |
| 2人が同時に［精算をやり直す］ | 1回分。後の方は何も変わらない |
| 2人が同じ金額待ちに金額を入れる | 後に届いた方の金額になる（ふつうの上書き）。「金額: 〇〇」は後の人 |
| 2人が同じ行を［来月に回す］ | 「どの月から回すか」を一緒に送り、すでに回っていたら何もしない（2か月進まない） |
| 2人が同時に出す額を決める | ［この額で決める］は決まっていない人だけを埋めるので重ならない。S-21 の［決める］は後に届いた方の手取りになり、「決めた: 〇〇」も後の人（割合はその月に保存した値のまま） |
| 2台が同時にその月を開く | `ensure_month` はひな形 × 対象月の一意制約で、二重に作らない |
| 相手が［精算をやり直す］した直後に、チェックを押した | 何もせず、締め待ちの画面に描き直す（`settle_set_check` が `blocked: not_locked`） |
| オフラインで保留した記録を、つながってから送る | 端末で決めた ID で送るので、送り直しても二重にならない。その月がもうロックされていたら「送れませんでした」（仕様書 §3.6） |
